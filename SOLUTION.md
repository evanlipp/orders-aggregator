# Решение

## Что сделано

1. **Скидки в статистике**
   - Внешний `Order` расширен полями `discountPercent` и `amountPaid` (оба необязательны для
     обратной совместимости).
   - В таблицу `orders` добавлена колонка `amount_paid_kop` (миграция `002_order_amount_paid.sql`).
   - `Order`/репозиторий/`OrdersService.normalize` сохраняют сумму до скидки (`amountKop`,
     gross) и фактически оплаченную сумму (`amountPaidKop`, net).
   - `GET /customers/:id/daily-totals` теперь отдаёт
     `{ date, total, gross, discount, net }`, где `total = gross`, `discount = gross - net`.
   - Добавлены тесты на скидки и на переход DST.

2. **Исправление расхождения для `c_7`**
   - Причина: смещение таймзоны считалось один раз для момента запроса
     (`tzOffsetMinutes(timezone, new Date())`) и применялось ко всем заказам. Для дат вокруг
     перехода на летнее время (Европа/Берлин: 29.03.2026) смещение меняется с +1 на +2 часа,
     поэтому часть заказов попадала в соседний день.
   - Исправление: смещение считается для каждого заказа отдельно —
     `tzOffsetMinutes(timezone, o.createdAt)`.

## Как нашли причину

- Жалоба указывала только конец марта и только часть дней, остальные совпадают до копейки.
- В `TotalsService.daily` обнаружено использование одного `offset`, вычисленного через
  `new Date()` (момент запроса), вместо времени заказа.
- Клиент `c_7` живёт в `Europe/Berlin`; переход на CEST происходит 29.03.2026, поэтому
  дни 27–31.03 затрагиваются, а более ранние периоды (зимнее время) — нет.
- Проверено утилитой `tzOffsetMinutes`: для `Europe/Berlin` 27.03 → 60 минут, 29.03 → 120 минут.

## Дополнительные наблюдения

- Внешний API (`orders-mock`) отдаётся обфусцированным JavaScript-ом; на хосте он не
  запускался, использовался только через Docker. Контейнер запускался с ограничением прав
  (`--cap-drop ALL`, `no-new-privileges`) и без монтирования хостовых путей.
- В `HttpOrdersApi` лимит по умолчанию 4 rps вместо документированных 5 rps, а ответ
  `{ "error": "rate_limited" }` трактуется как rate limit для любого тела с полем `error`.
  Это может скрывать другие ошибки API; в рамках задания не менялось.
- `toKop` отбрасывает доли копейки (`Math.floor`). Для входных сумм с точностью до
  копейки это корректно, но при появлении более точных значений приведёт к потере.
- `parseUtc` корректно трактует строки без зоны как UTC (по контракту API).

## Допущения

- Если `amountPaid` не передан, он считается равным `amount` (скидка 0%).
- `discountPercent` сохраняется только для совместимости схемы; расчёт `net` ведётся по
  `amountPaid`, как указано в требованиях (`net = amountPaid`).
- Период запроса `from..to` считается в календарных датах клиента; дни без заказов
  отдаются с нулями.
